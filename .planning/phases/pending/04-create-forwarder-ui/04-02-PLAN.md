**A. `MXRouteManagerApp.swift`** — create one `CreateForwarderModel` that outlives any single popover session:

```swift
@main
struct MXRouteManagerApp: App {
    @State private var settings: AppSettings
    @State private var createModel: CreateForwarderModel

    init() {
        let settings = AppSettings()
        _settings = State(initialValue: settings)
        _createModel = State(initialValue: CreateForwarderModel(settings: settings))
    }

    var body: some Scene {
        MenuBarExtra("MXRoute Manager", systemImage: "envelope.badge") {
            MenuBarContentView()
                .environment(settings)
                .environment(createModel)
        }
        .menuBarExtraStyle(.window)

        Settings {
            SettingsView()
                .environment(settings)
        }
    }
}
```

Why the `init()` dance rather than two inline initializers: `CreateForwarderModel` needs the *same* `AppSettings` instance the rest of the app observes, and one stored property cannot reference another in its inline initializer. Why app scope rather than `@State` inside the view: the model caches the domain list and the last-loaded mailboxes, and that cache is exactly what makes the second forwarder of the day appear instantly. A view-owned model is also awkward to build, since it needs `settings` from the environment before `@State` exists.

Do NOT inject `createModel` into the `Settings` scene — `SettingsView` has no use for it and this plan does not touch that file.

**Domain field (UI-01, #18).** A caption label plus a state switch:

```swift
Label("Domain", systemImage: "globe")   // caption, secondary
switch model.domains {
case .idle, .loading:
    HStack(spacing: 6) {
        ProgressView().controlSize(.small)
        Text("Loading domains…").font(.caption).foregroundStyle(.secondary)
    }
case .failed(let message):
    VStack(alignment: .leading, spacing: 6) {
        Text(message).font(.caption).foregroundStyle(.red)
        Button { Task { await model.loadDomains(force: true) } }
            label: { Label("Retry", systemImage: "arrow.clockwise") }
            .controlSize(.small)
    }
case .loaded(let domains) where domains.isEmpty:
    Text("No domains on this account.").font(.caption).foregroundStyle(.secondary)
case .loaded(let domains):
    Picker("Domain", selection: $model.selectedDomain) {
        ForEach(domains, id: \.self) { Text($0).tag($0) }
    }
    .labelsHidden()
    .pickerStyle(.menu)
}
```

`force: true` on retry is essential — plain `loadDomains()` early-returns when a previous `.loaded` is cached, so a non-forced retry after a *failure* would work but a retry after a stale success would silently do nothing.

**Domain-change reload (UI-03, #20).** On the outer `VStack` in `body`, alongside the existing `.task`:

```swift
.task(id: model.selectedDomain) {
    guard settings.isConfigured else { return }
    await model.loadAccounts(for: model.selectedDomain)
}
```

`.task(id:)` — not `.onChange` + `Task {}` — because it cancels the previous load when the id changes. Plan 04-01's `Task.isCancelled` guards depend on that cancellation to avoid painting a stale error. Note this fires once on appear too (with the remembered domain), which is exactly right: the mailboxes for the pre-selected domain start loading immediately.

Add `actionSection`, switching on `model.submitState` (UI-04, #21):

```swift
@ViewBuilder
private var actionSection: some View {
    switch model.submitState {
    case .succeeded(let forwarder):
        VStack(alignment: .leading, spacing: 8) {
            Label("Forwarder created", systemImage: "checkmark.circle.fill")
                .symbolRenderingMode(.multicolor)
                .font(.subheadline.weight(.semibold))
            Text("\(forwarder.email) → \(forwarder.destinations.first ?? model.selectedDestination)")
                .font(.callout)
                .textSelection(.enabled)
                .lineLimit(2)
            Button("Create Another") {
                model.reset()
                aliasFocused = true
            }
            .keyboardShortcut(.defaultAction)
        }
    default:
        VStack(alignment: .leading, spacing: 8) {
            HStack(spacing: 8) {
                Button {
                    Task { await model.submit() }
                } label: {
                    Label("Create Forwarder", systemImage: "arrow.turn.down.right")
                }
                .buttonStyle(.borderedProminent)
                .disabled(!model.canSubmit)
                .keyboardShortcut(.defaultAction)

                if model.submitState == .submitting {
                    ProgressView().controlSize(.small)
                }
            }
            if case .failed(let message) = model.submitState {
                Label(message, systemImage: "exclamationmark.triangle.fill")
                    .font(.caption)
                    .foregroundStyle(.red)
                    .fixedSize(horizontal: false, vertical: true)
            }
        }
    }
}
```

Points that are load-bearing rather than cosmetic:

- **The success text reads `forwarder.email` and `forwarder.destinations.first`, i.e. what came back from the create call** — not `model.aliasInput` and not the raw typed text. The alias is lowercase-normalized before it is sent, so echoing the input could show `Sales@…` for a forwarder that actually exists as `sales@…`. (`MXRouteClient.createForwarder` synthesizes this value when the API returns its documented empty 201, so it is always populated.) The `?? model.selectedDestination` is a belt-and-braces fallback for a server response with an empty destinations array.
- **The failure branch leaves the form intact and visible.** The user fixes the alias (or picks another destination) and presses Create again — a failure must never wipe what they typed. This is also why `submit()` sets `.failed` rather than resetting.
- **`.disabled(!model.canSubmit)`** is the whole of UI-02's "Create disabled until valid"; `canSubmit` also goes false while `.submitting`, so a double-press cannot create two forwarders. Do not add a second guard in the view.
- **`.keyboardShortcut(.defaultAction)`** makes Return create (and, in the success state, makes Return start the next one). Combined with Task 2's `.onSubmit` on the text field, the whole flow is keyboard-only: open, type, Return.
- `.fixedSize(horizontal: false, vertical: true)` on the error label so a long API message wraps inside 320pt instead of being truncated to uselessness — the decoded MXRoute message is the one thing that tells the user what went wrong.

Also handle one edge in `formSection`: when `model.submitState` is `.succeeded`, hide the input fields and show only the confirmation, so the popover reads as a result rather than a half-filled form. In `body`:

```swift
if settings.isConfigured {
    if case .succeeded = model.submitState {
        actionSection
    } else {
        formSection
        actionSection
    }
} else {
    unconfiguredSection
}
```

Constraints:

- Do NOT auto-dismiss the popover after a successful create. The confirmation IS the demo, and a popover that vanishes leaves the user unsure whether it worked.
- Do NOT add a toast, `NSAlert`, or notification. Errors and confirmations are inline in the popover.
- Do NOT clear the domain or destination selection in `reset()` (that is the model's decision, already made in 04-01) and do not clear them here either — the repeat case reuses both.
- Do NOT call `model.submit()` outside a `Task { }`; it is an `async` method on a MainActor model, and the button action is synchronous.
- Do NOT add retry-with-backoff or auto-retry on failure. One button press, one request.
