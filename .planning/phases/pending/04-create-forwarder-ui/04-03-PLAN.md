  <action>
Restyle `MenuBarContentView` to the spec below. This is a styling pass — do not change which states exist, what they say, or how loading/submitting works. Behavior is settled; only its presentation changes.

**Aesthetic target:** a compact native macOS menu bar utility — think the Wi-Fi or Control Center popover, or Bartender/Ice. Translucent, tight, one accent, generous vertical rhythm, no chrome for its own sake. No cards-inside-cards, no gradients, no shadows, no custom fonts, no emoji.

**1. Banded layout (replaces the single `.padding(16)`).** A full-bleed divider above the footer is impossible with one outer padding, so switch to three padded bands inside a zero-spacing root:

```swift
VStack(alignment: .leading, spacing: 0) {
    header
    content
        .padding(.horizontal, 16)
        .padding(.bottom, 14)
    Divider()
    footer
        .padding(.horizontal, 12)
        .padding(.vertical, 8)
}
.frame(width: 320)
.background(.regularMaterial)
```

- `header`: `HStack(spacing: 7) { Image(systemName: "arrow.turn.down.right").font(.system(size: 12, weight: .semibold)).foregroundStyle(.tint); Text("New Forwarder").font(.headline); Spacer() }` with `.padding(.horizontal, 16).padding(.top, 14).padding(.bottom, 12)`.
- `content` is the existing configured/unconfigured branch, in a `VStack(alignment: .leading, spacing: 14)` — 14pt between field groups.
- Inside each field group: `VStack(alignment: .leading, spacing: 5)` — label, then control, then (for the alias) the reserved caption row. 5pt label-to-control and 14pt group-to-group is the contrast that makes the grouping legible without any boxes or dividers between fields.
- The footer keeps its two buttons; give them `.buttonStyle(.borderless)` and `.controlSize(.small)`, and `.foregroundStyle(.secondary)` on Quit so Settings reads as the primary of the two.

**2. Material background.** `.background(.regularMaterial)` at the root is the UI-05 requirement, and it is also the one choice that can look wrong on the real `MenuBarExtra(.window)` chrome — if the panel already supplies vibrancy, a second layer reads slightly muddy. Ship it as written; the checkpoint in Task 2 asks the user directly. **Documented fallback, one line:** if the user says it looks flat, grey, or double-layered, delete the `.background(.regularMaterial)` modifier and let the panel's own chrome show through. Do not attempt `.ultraThinMaterial`, `NSVisualEffectView`, or a custom `NSPanel` — that is a rabbit hole for a cosmetic difference.

**3. SF Symbols.** Every label and status line is symbol-led, using these exact names (all standard system symbols):

| Where | Symbol |
| --- | --- |
| Header | `arrow.turn.down.right` |
| Domain label | `globe` |
| Alias label | `at` |
| Destination label | `tray.and.arrow.down` |
| Retry buttons | `arrow.clockwise` |
| Create button | `arrow.turn.down.right` |
| Success | `checkmark.circle.fill` with `.symbolRenderingMode(.multicolor)` |
| Inline error | `exclamationmark.triangle.fill` |
| Unconfigured nudge | `key` |
| Settings (footer) | `gearshape` |

Field labels use `Label(...)` with `.font(.caption.weight(.medium))`, `.foregroundStyle(.secondary)`, and `.imageScale(.small)` so the glyph does not out-weigh its caption. Do not invent symbol names — a name that does not exist renders as an empty box and the build will NOT warn you.

**4. Typography scale** — exactly four steps, applied consistently:

- `.headline` — the popover title, nothing else.
- `.subheadline.weight(.semibold)` — the "Forwarder created" line.
- default body — picker and text-field contents (leave them alone; system controls set their own type).
- `.caption` — field labels (`.weight(.medium)`, secondary), helper text, validation reasons, and inline errors.

Two deliberate exceptions, because these two strings are addresses and should be scannable rather than prose:
- the live `alias@domain` preview under the alias field → `.font(.system(.caption, design: .monospaced))`
- the confirmation route → `.font(.system(.callout, design: .monospaced))`

**5. Color.** Semantic styles only: `.primary`, `.secondary`, `.tint`, `.red`, and materials. No `Color(red:green:blue:)`, no hex, no `Color(white:)`, no `.black`/`.white` fills — those are exactly what breaks in the other appearance. `.red` is reserved for real errors (validation reasons and API failures); helper and preview text stays `.secondary`. The Create button stays `.borderedProminent` so it picks up the user's accent colour.

**6. Motion.** On the `content` band:

```swift
.animation(.snappy(duration: 0.2), value: model.submitState)
.animation(.easeInOut(duration: 0.15), value: model.domains)
.animation(.easeInOut(duration: 0.15), value: model.accounts)
```

Both enums are `Equatable` (plan 04-01), so these compile as written. This is why the form → confirmation swap glides instead of snapping, and why the spinner → picker transition does not flash. Do NOT animate on `model.aliasInput` — animating per keystroke makes typing feel laggy.

**7. Sizing discipline.** Keep `.frame(width: 320)` and set no height. The alias caption row stays reserved (`Text(" ")` when there is nothing to say) so typing never resizes the popover. Give the confirmation route `.lineLimit(2)` and `.fixedSize(horizontal: false, vertical: true)`, and the inline error `.fixedSize(horizontal: false, vertical: true)`, so long strings wrap within 320pt rather than truncating.

Constraints:

- Do NOT change any user-facing string's meaning, remove a state branch, or alter the `.task` / `.task(id:)` loads.
- Do NOT introduce a `Form`, `GroupBox`, or `List`. All three add macOS inset chrome that fights a 320pt popover; the hand-built `VStack` bands are the compact look this needs.
- Do NOT set `.preferredColorScheme` anywhere — the popover must follow the system appearance, which is the entire point of the Light/Dark check.
- Do NOT add hover effects, custom button styles, or a close/dismiss button.
- Do NOT touch `SettingsView` — its own look is settled and Phase 5 owns any further polish.
- Keep the `#Preview` from plan 04-02 (the credential-less `makeClient`), so opening the canvas still cannot fire a request.

Walk the user through these and ask them to confirm each:

Now type `my alias` — the reason changes to the spaces message. Now `sales.team` — the red line is replaced by a grey `sales.team@<their domain>` preview and Create becomes available. Ask them to confirm the address and destination are exactly right.
5. **Real?** Have them confirm the forwarder actually exists — `panel.mxroute.com` → that domain → Forwarders. This is the claim no test in this repo can make.
6. **Repeat + error path.** Press **Create Another** — the alias field clears and is focused, the domain and destination stay as they were. Type `kata-test-1` again and press Return: this time MXRoute rejects the duplicate and the message appears inline in red inside the popover, with the form still filled in. Ask them to confirm the message is MXRoute's own words, not a generic failure and not raw JSON.
7. **Speed.** Press Create Another, type `kata-test-2`, Return. Time it from clicking the menu bar icon: the whole thing should be comfortably under ten seconds, with the domain and destination already remembered. Ask them to confirm.
8. **Persistence.** Quit the app (footer Quit), relaunch it (`open /tmp/mxrm-build/Build/Products/Debug/MXRouteManager.app`), open the popover: the Domain menu comes back pre-set to the domain they last used.
9. **Light + Dark (UI-05).** With the popover open, switch System Settings → Appearance between Light and Dark. Ask about **both**: is the background translucent and native-looking (not flat grey, not double-layered/muddy), is every label and message readable, and does the accent-coloured Create button look right? 10. **Icons.** Ask them to confirm every row icon actually draws (globe, @, tray, gear) — an empty rectangle means a mistyped SF Symbol name, which the build does not catch.
11. **Cleanup.** Remind them they can delete `kata-test-1` and `kata-test-2` in the MXRoute panel. Leaving them costs nothing; it is their call.

Troubleshooting if something fails:

- Domains never load, error mentions reaching MXRoute → confirm the entitlement survived: `codesign -d --entitlements - --xml /tmp/mxrm-build/Build/Products/Debug/MXRouteManager.app | plutil -p -` must show `com.apple.security.network.client => 1`.
- "Add your server, username, and API key in Settings first." → the Keychain read returned nothing; check Settings still shows "API key stored in Keychain".
- The destination menu is blank but the domain has mailboxes → the picker's `tag` type and the selection type disagree (both must be `String`, the account's `email`).
- Create stays disabled with a valid-looking alias → `selectedDestination` is empty; the accounts load probably failed silently.
- Switching domains shows an error banner that disappears on its own → a cancelled load is writing state; the `Task.isCancelled` / `domain == selectedDomain` guards in `loadAccounts` are missing.

Scope discipline: complaints about the *first-run* experience, empty-state wording, the app icon, or the README are Phase 5 (POL-01/POL-02) and become issues rather than fixes here.
