  <name>Task 1: Implement KeychainService</name>
  <files>MXRouteManager/Services/KeychainService.swift</files>
  <action>
Create `MXRouteManager/Services/KeychainService.swift` importing only `Foundation` and `Security`.

Shape:

```swift
struct KeychainService {
    enum KeychainError: Error, LocalizedError {
        case unexpectedStatus(OSStatus)
        case invalidData
        var errorDescription: String? { ... }
    }

    static let shared = KeychainService()

    private let service: String
    private let account: String

    init(service: String = "MXRouteManager", account: String = "api-key") {
        self.service = service
        self.account = account
    }

    func save(_ apiKey: String) throws
    func load() throws -> String?
    func delete() throws
    var hasKey: Bool { get }   // ((try? load()) ?? nil) != nil
}
```

Behaviour, exactly:

- `save(_:)` — build the base query `[kSecClass: kSecClassGenericPassword, kSecAttrService: service, kSecAttrAccount: account]`. First try `SecItemUpdate(baseQuery, [kSecValueData: Data(apiKey.utf8)])`. On `errSecItemNotFound`, call `SecItemAdd` with the base query plus `kSecValueData`. Any other non-`errSecSuccess` status throws `.unexpectedStatus`.
  Do NOT implement this as delete-then-add: if the add leg fails, the user's key is already gone and the app silently becomes unconfigured. Update-then-add can only fail forward.
- `load()` — `SecItemCopyMatching` with the base query plus `kSecReturnData: true` and `kSecMatchLimit: kSecMatchLimitOne`. `errSecItemNotFound` returns `nil` (absence is a normal state on first launch, NOT an error — callers branch on it constantly). `errSecSuccess` with data that is not valid UTF-8 throws `.invalidData`. Any other status throws `.unexpectedStatus`.
- `delete()` — `SecItemDelete(baseQuery)`; treat both `errSecSuccess` and `errSecItemNotFound` as success so deletion is idempotent. Other statuses throw.
- `errorDescription` for `.unexpectedStatus` should include the human-readable message from `SecCopyErrorMessageString(status, nil)` (falling back to the raw status number) so plan 02-03 can surface something better than "an error occurred".

Two constraints that are load-bearing, do not "improve" them away:

- Do NOT set `kSecUseDataProtectionKeychain: true`. That routes items to the data-protection keychain, where they are invisible in Keychain Access.app — and this phase's demo is "the key is visible in Keychain Access, not in UserDefaults". Default (file-based login keychain) behaviour is what we want.
- Do NOT add `kSecAttrAccessible`, access groups, `kSecAttrSynchronizable`, or an entitlements file. The file-based keychain ignores accessibility attributes, iCloud sync is wrong for a machine-local API key, and the sandboxed app already has the keychain access it needs (verified).

Also: no `print`/`NSLog` of the key or of loaded data anywhere, ever — this type handles the one secret in the app.

Do NOT add any caller yet. Nothing outside this file references `KeychainService` in this plan; plan 02-02 wires it into `AppSettings`.

<task type="auto">
  <name>Task 2: Prove the Keychain round-trip with unit tests</name>
  <files>MXRouteManagerTests/KeychainServiceTests.swift</files>
  <action>
Create `MXRouteManagerTests/KeychainServiceTests.swift` using Swift Testing (`import Testing`, `import Foundation`, `@testable import MXRouteManager`).

Every test MUST construct its own instance with an isolated service name:

```swift
private func makeService() -> KeychainService {
    KeychainService(service: "MXRouteManager.tests", account: "test-api-key")
}
```

Never use `KeychainService.shared` in a test. The shared instance points at the real `MXRouteManager` / `api-key` item — a test using it would delete the user's actual API key off their login keychain mid-run.

Each test must clean up with `defer { try? service.delete() }` so a failure does not leave residue in the login keychain for the next run.

Write four tests:

1. `saveThenLoadReturnsTheSameKey` — save `"test-key-abc123"`, `#expect(try service.load() == "test-key-abc123")`.
2. `savingTwiceOverwrites` — save `"first"`, save `"second"`, expect `load()` == `"second"` (this is the `SecItemUpdate` leg; without it the second save would fail with `errSecDuplicateItem`).
3. `loadReturnsNilWhenAbsent` — `try service.delete()` first, then `#expect(try service.load() == nil)`.
4. `deleteIsIdempotent` — call `delete()` twice on an absent item; neither call throws (`#expect(throws: Never.self) { try service.delete() }`).

Mark the suite `@Suite(.serialized)` — these tests share one Keychain item name and will interfere with each other if Swift Testing runs them in parallel, which it does by default.

Do not write tests for `AppSettings` or the Settings UI here; those types do not exist yet.
