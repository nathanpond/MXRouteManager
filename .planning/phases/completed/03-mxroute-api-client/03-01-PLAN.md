<task type="auto">
  <name>Task 1: Grant the sandboxed app outgoing network access</name>
  <files>MXRouteManager.xcodeproj/project.pbxproj</files>
  <action>
The app target has `ENABLE_APP_SANDBOX = YES` and **no** entitlements file. Without the `com.apple.security.network.client` entitlement every `URLSession` request from the app returns a "not permitted" `URLError` at runtime — silently in the UI, and only in the app (mocked tests would still pass), which is exactly the trap this task removes.

Use the sanctioned build-setting route, NOT a hand-authored `.entitlements` file. Xcode 26 exposes `ENABLE_OUTGOING_NETWORK_CONNECTIONS` (Boolean, category "App Sandbox & Hardened Runtime"), and it generates the entitlement the same way `ENABLE_APP_SANDBOX` generates `com.apple.security.app-sandbox`. This was verified during planning: building this exact project with `ENABLE_OUTGOING_NETWORK_CONNECTIONS=YES` produced an app signed with `com.apple.security.network.client: True`.

Edit `MXRouteManager.xcodeproj/project.pbxproj` and add this single line to **both** app-target build configurations:

```
				ENABLE_OUTGOING_NETWORK_CONNECTIONS = YES;
```

They are the two `XCBuildConfiguration` blocks whose `buildSettings` contain `ENABLE_APP_SANDBOX = YES;` and `PRODUCT_BUNDLE_IDENTIFIER = client.MXRouteManager;` — one named `Debug`, one named `Release` (around lines 406-465). Insert the line immediately after `ENABLE_APP_SANDBOX = YES;` in each, keeping the file's alphabetical ordering (`ENABLE_APP_SANDBOX`, `ENABLE_OUTGOING_NETWORK_CONNECTIONS`, `ENABLE_PREVIEWS`, `ENABLE_USER_SELECTED_FILES`) and the file's tab indentation.

Hard constraints:

- Do NOT create `MXRouteManager/MXRouteManager.entitlements` and do NOT set `CODE_SIGN_ENTITLEMENTS`. An entitlements file inside the synchronized group is a second thing to keep in sync with the build settings, and Xcode's own UI writes the build setting instead.
- Do NOT touch any `PBXFileReference`, `PBXBuildFile`, `PBXFileSystemSynchronizedRootGroup`, or `PBXFileSystemSynchronizedBuildFileExceptionSet` entry. Build settings only. Anything else risks corrupting a synchronized-groups project.
- Do NOT add `ENABLE_INCOMING_NETWORK_CONNECTIONS` (that is the server entitlement; this app only makes outgoing calls) and do NOT touch the test-target or UI-test-target configurations (unit tests run inside the host app and inherit its entitlements).
- Do NOT change `ENABLE_APP_SANDBOX` — the sandbox stays on.
  </action>

<task type="auto">
  <name>Task 2: Add the envelope, models, and typed error</name>
  <files>MXRouteManager/Models/MXRouteModels.swift</files>
  <action>
Create `MXRouteManager/Models/MXRouteModels.swift` (it joins the app target automatically — no pbxproj edit). Header comment in the style of the other files: this file is the wire format of the MXRoute API plus the one error type the UI renders.

Declare every type `nonisolated` so the client in plan 03-02 and the nonisolated test target can use them without actor hops. Give each one `Sendable`.

1. `nonisolated struct APIErrorBody: Decodable, Sendable, Equatable` with `let code: String`, `let message: String`, `let field: String?`.

2. `nonisolated struct APIEnvelope<T: Decodable & Sendable>: Decodable, Sendable` with `let success: Bool`, `let data: T?`, `let error: APIErrorBody?`.
   - Write a custom `init(from decoder:)`: `data` and `error` via `decodeIfPresent`, and `success` as `try container.decodeIfPresent(Bool.self, forKey: .success) ?? (error == nil)`.
   - WHY `data` is Optional: `POST /domains/{domain}/forwarders` answers `201` and the spec declares no response body, so a non-optional `data` would turn a successful create into a decoding error.

3. `nonisolated struct EmailAccount: Codable, Sendable, Equatable, Identifiable`:
   - `let username: String`, `let email: String`, `let quota: Int`, `let usage: Double`, `let limit: Int`, `let sent: Int`, `let suspended: Bool`; `var id: String { email }`.
   - Write BOTH an explicit memberwise `init(username:email:quota:usage:limit:sent:suspended:)` and a custom `init(from decoder:)`. Declaring `init(from:)` in the type body suppresses the synthesized memberwise init, and plan 03-03's tests plus Phase 4 previews need to build fixtures directly.
   - In `init(from:)`, decode `username` and `email` with `decode` (required — the picker in Phase 4 is meaningless without an address) and decode `quota`, `usage`, `limit`, `sent`, `suspended` with `decodeIfPresent`, defaulting to `0`, `0`, `0`, `0`, `false`. WHY: these are informational only; one absent counter on one mailbox must not blow up the whole account list.
   - `usage` is `Double`, not `Int` — the spec's example is `256.5` and an `Int` would fail to decode.

4. `nonisolated struct Forwarder: Codable, Sendable, Equatable, Identifiable`:
   - `let alias: String`, `let email: String`, `let destinations: [String]`; `var id: String { email }`.
   - Same pattern: explicit memberwise init plus `init(from:)` with `alias`/`email` required and `destinations` via `decodeIfPresent` defaulting to `[]`.

5. `nonisolated enum MXRouteError: Error, LocalizedError, Equatable, Sendable` with exactly these cases:

```swift
case notConfigured
case invalidRequest(message: String)
case network(message: String)
case unauthorized(message: String)
case api(code: String, message: String, field: String?)
case decoding(message: String)
case invalidResponse
```

   - WHY `network`/`decoding` carry a `String` instead of the underlying `Error`: `Equatable` conformance is what lets plans 02 and 03 assert exact mapping with `#expect(error == .api(code: "CONFLICT", ...))`, and an existential `Error` payload cannot be `Equatable`. Capture `underlying.localizedDescription` at the throw site.
   - Implement `var errorDescription: String?` — every case returns a sentence a user can act on:
     - `.notConfigured` → `"Add your server, username, and API key in Settings first."`
     - `.invalidRequest(let message)` → `message`
     - `.network(let message)` → `"Could not reach MXRoute: \(message)"`
     - `.unauthorized(let message)` → `message.isEmpty ? "MXRoute rejected these credentials." : message`
     - `.api(_, let message, let field)` → `field.map { "\(message) (\($0))" } ?? message`
     - `.decoding(let message)` → `"Could not read the MXRoute response: \(message)"`
     - `.invalidResponse` → `"MXRoute returned an unexpected response."`
   - Add `var code: String?` returning the API code for `.api`/`.unauthorized` (`"UNAUTHORIZED"`) and `nil` otherwise — Phase 4 wants to special-case `CONFLICT` (duplicate alias) without string-matching messages.

Constraints:

- No `URLSession`, no `URLRequest`, no networking of any kind in this file. The client is plan 03-02; a stub here would be torn out.
- Do NOT add a `CodingKeys` remapping/`keyDecodingStrategy` — the API's JSON keys are already flat lowercase and match the Swift property names exactly.
- Do NOT make `MXRouteError` conform to `CustomStringConvertible` on top of `LocalizedError`; the views read `errorDescription` / `localizedDescription`.
  </action>

Tests (one `@Test` each, all fed from inline JSON string literals taken from the OpenAPI examples):

1. `domainsEnvelopeDecodes` — `{"success":true,"data":["example.com","mydomain.org"]}` into `APIEnvelope<[String]>`: `success == true`, `data == ["example.com","mydomain.org"]`, `error == nil`.

3. `emailAccountToleratesMissingCounters` — `{"success":true,"data":[{"username":"a","email":"a@example.com"}]}` decodes with `quota == 0`, `usage == 0`, `limit == 0`, `sent == 0`, `suspended == false`.
4. `forwarderEnvelopeDecodes` — `{"success":true,"data":{"alias":"sales","email":"sales@example.com","destinations":["me@example.com"]}}`.

6. `errorEnvelopeWithoutFieldDecodes` — `{"success":false,"error":{"code":"UNAUTHORIZED","message":"Invalid API credentials"}}`: `error?.field == nil`.
7. `envelopeWithNoDataDecodes` — `{"success":true}` into `APIEnvelope<Forwarder>`: `success == true`, `data == nil` (this is the 201-create shape).
8. `errorDescriptionsAreUserReadable` — for `.notConfigured`, `.unauthorized(message: "Invalid API credentials")`, `.api(code: "CONFLICT", message: "Forwarder already exists", field: nil)`, `.api(code: "VALIDATION_ERROR", message: "Invalid alias", field: "alias")`, `.network(message: "The Internet connection appears to be offline.")`: each `errorDescription` is non-nil and non-empty; the `unauthorized` one equals the API message; the field-carrying one contains both `"Invalid alias"` and `"alias"`; the `.network` one contains the underlying text.
9. `errorCodeIsExposed` — `MXRouteError.api(code: "CONFLICT", message: "x", field: nil).code == "CONFLICT"` and `MXRouteError.notConfigured.code == nil`.
