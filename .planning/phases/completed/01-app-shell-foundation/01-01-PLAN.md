<task type="auto">
  <name>Task 1: Set macOS 15 deployment target and LSUIElement in build settings</name>
  <files>MXRouteManager.xcodeproj/project.pbxproj</files>
  <action>
Edit build settings only — no structural pbxproj changes.

1. Replace every `MACOSX_DEPLOYMENT_TARGET = 26.5;` with `MACOSX_DEPLOYMENT_TARGET = 15.0;`. There are four occurrences: the project-level Debug and Release configurations, and the `MXRouteManagerTests` Debug and Release configurations. The app target and UI test target inherit from the project level, so after this change every target builds against macOS 15.
2. In the two `MXRouteManager` APP-target build configurations (the ones containing `PRODUCT_BUNDLE_IDENTIFIER = client.MXRouteManager;` alongside `ENABLE_APP_SANDBOX = YES;` — one Debug, one Release), add the line `INFOPLIST_KEY_LSUIElement = YES;` immediately before the existing `INFOPLIST_KEY_NSHumanReadableCopyright = "";` line, matching the surrounding tab indentation. Xcode keeps build settings alphabetically sorted, and `LSUIElement` sorts before `NSHumanReadableCopyright`.

Add LSUIElement to BOTH configurations. If it lands only in Debug, the Release build in Phase 5 will show a Dock icon and nobody will notice until then.

Do NOT add `INFOPLIST_KEY_LSUIElement` to the test targets, and do NOT set the activation policy in Swift code (`NSApp.setActivationPolicy(.accessory)`). The success criterion is the declarative Info.plist route; a code-side policy change also causes a visible Dock-icon flash at launch.

`GENERATE_INFOPLIST_FILE = YES` is already set on the app target, so there is no Info.plist file to create or edit — the `INFOPLIST_KEY_*` build setting is the only lever.
  </action>

  <name>Task 3: Write the MenuBarExtra shell and placeholder popover content</name>
  <files>MXRouteManager/App/MXRouteManagerApp.swift, MXRouteManager/Views/MenuBarContentView.swift</files>
  <action>
Rewrite `MXRouteManager/App/MXRouteManagerApp.swift` so it imports only SwiftUI (no SwiftData, no ModelContainer, no WindowGroup) and its `body` is a single scene:

```swift
MenuBarExtra("MXRoute Manager", systemImage: "envelope.badge") {
    MenuBarContentView()
}
.menuBarExtraStyle(.window)
```

`.menuBarExtraStyle(.window)` is mandatory — the default `.menu` style renders a pull-down menu that cannot host the form Phase 4 needs. `envelope.badge` is a long-standing SF Symbol; if you substitute another, it must exist in SF Symbols 6 or the menu bar icon silently renders blank.

Do NOT add a `WindowGroup`. A menu-bar-only app that also declares a WindowGroup opens a stray empty window at launch.

Create `MXRouteManager/Views/MenuBarContentView.swift` with a `MenuBarContentView: View` that renders placeholder chrome:
- a headline title ("MXRoute Manager"),
- a secondary-foreground line stating that forwarder creation arrives in a later phase,
- a `Divider()`,
- a bottom row with a `Spacer()` and a "Quit" `Button` calling `NSApplication.shared.terminate(nil)` (add `import AppKit` alongside `import SwiftUI` rather than relying on transitive re-export),
- `.padding(16)` and `.frame(width: 320)` so the popover has a stable, compact size.

Leave a `// Settings entry point added in plan 01-02` comment in that bottom row — plan 01-02 inserts `SettingsLink` there.

The Quit button is not decoration: with no Dock icon and no main window, an unquittable menu-bar app is a real trap during manual verification.

Do NOT implement any settings fields, Keychain access, networking, or domain/alias UI. Phases 2-4 own those; placeholder text only.

Add a `#Preview { MenuBarContentView() }` to the view file. Do not leave a preview referencing `Item.self` or `modelContainer` anywhere.
